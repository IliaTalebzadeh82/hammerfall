# Phase 15 profiling milestone — causal evidence

2026-10-01. Measurements are short local Compose runs on a shared host, not
production capacity or an SLO. The API at the starting commit was
`3dff3b7e953c9cd12a84af35231f6548da8c8f4c`; Phase 15 diagnostic code
was in the working tree for these runs. Each `p14-*` run ID was generated by
the unchanged Phase 14 fixture naming convention. No concurrency, pool,
auction or publisher setting was tuned.

## Hot request admission and DB checkout

[Unprofiled 64-VU diagnostic run](p14-20261001T153137Z-407ec589-hot/report.md):
`PROFILE_RUNTIME=true load-tests/benchmark.sh hot 64 20s`. It completed
2,500 HTTP requests at 117.22/s, HTTP p50/p95/p99 523.24/781.90/855.31 ms,
39 accepted mutations and 1,211 expected domain rejections, with zero
unexpected HTTP errors and zero PostgreSQL checker failures. The 109 runtime
samples showed Puma backlog median 58, peak 61 (sampled `backlog_max` peak
62), busy-thread statistic median 61 and capacity median 0. Puma's
`busy_threads` includes queued jobs in this version; it is **not** a count
of executing threads. The process had three request threads and sustained
queue pressure. The sampler's own control queries reset Puma's interval
`backlog_max`; snapshots are not request admission times.

The Active Record checkout histogram advanced 5,133 samples; all fell in
the ≤1 ms bucket. The blocking queue-wait histogram had no samples. Pool
state gauges sampled at checkout start are sparse and can miss a brief wait.
Auction-lock `place_bid` had 1,250 samples, p95 ≤10 ms bucket, and bid
processing p95 ≤50 ms for accepted and rejected outcomes. The single during
snapshot found no PostgreSQL lock waiter. These are component observations,
not additive per-request traces. Puma 8.0.2 exposes backlog/thread stats but
this configuration provides no supported timestamp from socket acceptance
through Rack entry. Therefore exact per-request pre-Rack delay remains
unmeasured. A sustained ~58-request backlog at ~117 HTTP/s suggests roughly
half a second of queueing by a queue-length/rate estimate, but that estimate
assumes a stable arrival/service process and is not an observed latency
percentile. This is the strongest current explanation for most of the hot
HTTP tail; DB checkout and auction-lock wait did not dominate this run.

## CPU, allocations and memory

[CPU-profiled hot run](p14-20261001T153701Z-0474034d-hot/report.md):
`PROFILE_RUNTIME=true PROFILE_CPU=true load-tests/benchmark.sh hot 64 20s`.
It passed the PostgreSQL checker with zero HTTP errors. CPU profiling is an
extra intervention, so its 102.58 HTTP/s and 959.76 ms p95 should not be
treated as a clean before/after result against the unprofiled run.

The [compressed StackProf dump](p14-20261001T153701Z-0474034d-hot/cpu.stackprof.dump.gz)
has 20,075 CPU samples with 4.02% missed samples. `Dir.[]` (7.9% self)
and `File.mtime` (3.8% self) are called from
`ActiveSupport::FileUpdateChecker`; its `updated?` path accounted for
13.3% inclusive samples. This is development code reloading work and a
measured local CPU cost, not evidence to disable production behavior.
`PG::Connection#exec` had 4.3% self samples; GC had 5.24% of samples.
No single application-domain method dominated the CPU profile. One API
core was busy in the hot runs, consistent with Puma's fixed three-thread
service rate and request queue growth.

[GC counters](p14-20261001T153701Z-0474034d-hot/gc.json) over the
20-second profile rose by 5,067,570 total allocated objects and 105 GC
cycles (97 minor, 8 major). Live heap slots **fell** by 14,822 across the
window. The profiler run's sampled RSS reached ~194 MiB and settled near
174 MiB after load, while the unprofiled diagnostic run had ~132–137 MiB
during load and 113 MiB at its later snapshot. Profiler retention and
different start states make these runs unsuitable for a leak comparison.
The Phase 14 ~130→200 MiB plateau and this non-monotonic behavior do not
establish a leak. A longer same-process post-load observation and allocation
source profile remain worthwhile before a memory optimization.

## Query shapes

The [isolated query probe](phase-15-query-profile.json) ran through the Rails
Rack app and actual PostgreSQL with an `sql.active_record` subscriber. It
reported only query categories and timing, with no SQL text, binds, private
maximums or command keys. It bypassed Puma sockets and did not reproduce hot
contention. The first accepted command was cold (36 queries, 113.65 ms Rack,
31.59 ms SQL) and should not be mixed with warm path cost.

| Warm path | Queries | SQL total | Rack elapsed | Outcome |
|---|---:|---:|---:|---|
| Accepted manual | 22 | 13.42 ms | 31.80 ms | 201 |
| Rejected stale | 15 | 3.29 ms | 10.28 ms | 422 |
| Maximum bid | 17 | 4.36 ms | 15.43 ms | 200 |
| Competing maximum | 24 | 7.26 ms | 16.96 ms | 200 |
| Manual bid with competing proxy | 22 | 7.03 ms | 17.39 ms | 201 |
| Completed idempotent replay | 5 | 0.96 ms | 4.34 ms | 201 replay |

The largest warm query group was a few milliseconds, without an identified
slow query or N+1. The proxy case did more useful work but remained much
smaller than the hot HTTP tail. An index or proxy rewrite is not justified
by these observations. The probe is explanatory, not a production traffic
distribution or concurrent SQL percentile.

## FD and Action Cable

[200-subscriber fanout](p14-20261001T154218Z-e0ba815f-fanout/report.md):
`PROFILE_RUNTIME=true load-tests/benchmark.sh fanout 200 20s`. All 200
subscriptions confirmed, k6 saw 5,800 invalidations and zero socket failures;
the PostgreSQL checker found zero failures. At peak the API had 226 FDs,
including 209 socket FDs and 202 TCP sockets with local HTTP port 3000.
The API went from 20 FDs before to 23 after. The 64-VU hot run similarly
peaked at 86 FDs and returned to 20 after. These short samples support
roughly one FD per active client connection and show cleanup after load;
they cannot exclude a slow leak. The Phase 14 500-socket sample near 522
FDs and 1,000-contender `EMFILE` at the 1,024 soft limit fit this mechanism.
The 200-subscriber handshake p95 was 847 ms, and Puma's sampled backlog
peaked at 190 during establishment. Shared admission pressure is plausible;
the run does not isolate handshake CPU or Redis as a primary cause. An
isolated higher-FD-limit challenge may expose the next limit, but a higher
production setting is not adopted here.

## Causal decisions and remaining measurements

- **Confirmed local contributor:** Puma request admission backlog under hot
  load; development Rails file checks consume meaningful CPU. No concurrency
  change is adopted yet.
- **Not supported as dominant:** DB connection queue wait (no blocking samples),
  auction row-lock wait (≤10 ms hot p95 bucket), isolated warm SQL cost,
  publisher delivery (Phase 14 bounded durations and drained backlog).
- **FD mechanism:** concurrent HTTP/WebSocket sockets consume the ordinary
  1,024-process soft limit; no short-run FD leak signal.
- **Inconclusive:** exact per-request pre-Rack delay; diagnostic overhead;
  longer-term RSS retention; contention-specific query shapes; precise
  production-relevant throughput; the primary contributor to the 500-socket
  handshake tail. No controlled telemetry on/off or raised-FD experiment yet.

Next milestone: run isolated, repeated diagnostic on/off and Puma concurrency
experiments if the baseline comparison supports them, keeping the DB pool
fixed first. Measure resource cost, accepted useful work, tails, Puma backlog,
checkout and lock wait, then run the authoritative checker. Treat Rails
development reloading as a local-runtime variable, not an auction change.
