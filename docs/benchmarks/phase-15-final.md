# Phase 15 final performance review

Phase 15 investigated the hot-auction HTTP tail left by [Phase 14](phase-14-final.md): roughly 935 ms p95 in one local 64-VU run despite an auction-lock p95 bucket of at most 25 ms. The [Session 1 profile](phase-15-session-1.md) and [Session 2 comparisons](phase-15-session-2.md) are the measurement records. These are short comparative runs on a shared local Compose host, not production capacity, an SLO, safe user count, or cloud sizing evidence. All 26 Session 2 hot runs had zero unexpected HTTP outcomes and passed the authoritative PostgreSQL checker.

## Causal model

Session 1 added Puma backlog and thread statistics, Active Record checkout and blocking queue timings, CPU/GC profiles, real-PostgreSQL query probes, and process FD composition. With three Puma request threads and pool three, a 64-VU hot run saw median backlog 58, capacity median zero and 782 ms HTTP p95. This supports admission pressure, but Puma exposes no supported timestamp from socket acceptance to Rack entry; exact per-request pre-Rack latency remains unmeasured. Backlog length divided by throughput is only a conditional queueing estimate, not an observed latency percentile.

DB checkout was in the ≤1 ms p95 bucket without blocking pool waits. Auction row-lock p95 was ≤10 ms in the clean diagnostic run. Warm isolated SQL totals were 0.96–13.42 ms across representative paths; no material query or proxy-resolution hotspot appeared. These measurements do not make the HTTP tail an additive sum or prove admission is its only cause. They rule out lock wait and baseline DB checkout as dominant measured causes. No auction concurrency redesign or index/query rewrite was attempted.

The CPU profile attributed 13.3% inclusive samples to development file update checks. Turning off only request reloading in development cut that path to 2.9% inclusive (remaining migration checks). In three repeated runs each, disabled reloading produced 166–179 HTTP/s and 2.67–2.80 accepted mutations/s versus 146–158 HTTP/s and 2.28–2.49 accepted/s with reloading enabled. HTTP p95/p99 ranges overlapped and Puma backlog stayed near 57. This is a measured local development CPU cost and useful-work gain, not a demonstrated tail fix or a full production-mode comparison. Normal development reloading remains enabled.

The diagnostic ON/OFF control did not establish repeatable material hook overhead; external polling and CPU profiling are separate interventions. Turning API OTel off in a cleaner local window raised HTTP rate to 184–211/s versus 159–179/s with it on, but tail, CPU and memory did not show an equally stable gain. OTel remains enabled in the measured local stack because request, domain, outbox, lock, pool and failure visibility is worth retaining. The comparison measures the complete OTel-enabled path, including diagnostic metrics; it does not isolate a single tracer operation.

## Experiment decisions

| Experiment | Hypothesis and baseline | Change, repeated result and resource effect | Decision |
|---|---|---|---|
| Diagnostic hooks | Hooks might distort the three-thread baseline | Three ON and three OFF runs overlapped after one low ON outlier; all checkers passed | **ADOPT** bounded opt-in diagnostics; overhead magnitude **INCONCLUSIVE** |
| Development reloading | Request file checks consume CPU | Three enabled/disabled pairs improved accepted work with reloading off; tails overlapped, backlog stayed high; all checkers passed | **REJECT** changing ordinary development behavior for benchmark gain; retain opt-in switch |
| API OTel | Telemetry adds work | Five ON, three OFF comparisons showed directional throughput gain with OTel off, without stable tail/resource improvement; all checkers passed | **REJECT** disabling OTel; **DEFER** targeted cost work if production evidence warrants it |
| Five Puma threads, pool three | More request concurrency may reduce admission pressure | Two runs produced 2,292–2,298 blocking pool waits/run, checkout p95 ≤25 ms and lower useful work; all checkers passed | **REJECT** five-thread setting |
| Five Puma threads, pool five | Removing induced checkout waits may improve end-to-end work | Two runs had zero pool waits, two more PostgreSQL sessions and no repeatable useful-work or tail gain; all checkers passed | **REJECT** larger pool |
| Auction lock / query rewrite | Lock or SQL could dominate tail | Measured lock and isolated SQL were small beside HTTP tail; no change or after case | **DEFER** redesign absent new production evidence |
| Raised FD ceiling | A higher limit might expose a later resource ceiling | Not run; existing socket composition explains observed pressure | **INCONCLUSIVE** beyond recorded local ceiling |

The thread/pool sequence demonstrates bottleneck migration: more Puma concurrency admitted more simultaneous Rails work and created DB pool waiting. Enlarging the pool removed that wait and consumed more connections, yet produced no repeatable end-to-end gain. The restored three-thread baseline itself slowed to roughly 113 HTTP/s in the later host window, compared with 146–179/s earlier. That drift prevents a clean cross-window percentage attribution. No thread, pool, worker, FD, auction, publisher or production runtime tuning was adopted.

## Resources and retained controls

The local API process had a 1,024 soft and 524,288 hard FD limit. At 200 Cable subscribers it reached 226 FDs, including 202 HTTP sockets, and returned from 20 before to 23 after. The hot run returned from a peak of 86 to 20. Phase 14's 1,000-contender `EMFILE` and timeouts met this process/socket ceiling; they were not a PostgreSQL capacity result. A 600-contender final-ten burst was the largest clean local observation. No short-run FD leak was demonstrated; larger WebSocket fanout remains unresolved. Session 2 did not run a raised-FD experiment.

Session 1's CPU-profiled run allocated 5.07 million objects over 20 seconds while live heap slots fell by 14,822. Its RSS settled below its peak; Session 2's restarted-container snapshots were roughly 110–135 MiB. RSS high-water behavior, allocator retention and profiler overhead cannot establish a retained-object or long-term memory leak. A longer same-process observation and allocation-source profile remain open if operational data motivates them.

Ordinary local Compose uses one API Puma process, three request threads and an Active Record pool of three; Rails development reloading is on. The measured stack kept API OTel on, while the Compose default is `OTEL_ENABLED=false` unless explicitly configured. `PERFORMANCE_DIAGNOSTICS=false`, `PERFORMANCE_CPU_PROFILE=false` and `PERFORMANCE_DISABLE_RELOADING=false` are the defaults. The private Puma Unix socket and DB checkout/pool metrics are **RETAIN** as bounded opt-in diagnostics; the socket directory is owner-only mode 0700 and the socket mode 0600. StackProf is **RETAIN** as a development-only, explicit, bounded trigger. The external sampler and sanitized query probe are **RETAIN** local tools. OTel is **NORMAL OBSERVABILITY**. The five-thread/pool-five overrides were removed; no temporary experiment configuration remains in normal runtime.

The DB pool modules are prepended at boot even when diagnostics are off, but return directly to `super` after one flag check; no pool timing, state sampling or histogram recording occurs. This small permanent dispatch cost is intentionally retained for a runtime diagnostic switch. The ON/OFF control did not establish a stable material penalty, but cannot prove zero overhead.

Future investigation should start with production-relevant Puma admission, CPU profiles, checkout/queue measurements and end-to-end correctness, then test any resource change as a whole system. Exact pre-Rack per-request time, production worker/thread/pool sizing, long-term memory behavior and larger WebSocket capacity remain unmeasured. Nothing here establishes production throughput, globally representative latency, Kubernetes/GCP sizing or maximum fanout.
